# Problem: ESP32-S3 / IDF 5 TMC SPI initialization hangs because no transfer is started

Published: https://github.com/bdring/FluidNC/issues/1930

## Summary

On a PiBot V5.88 Ultra with TMC5160 drivers, FluidNC v4.1.1 hangs during
startup after printing all axis/motor/limit descriptions. There are no TMC
driver-test results and no `Kinematic system: Cartesian` message.

The cause appears to be `tmc_spi_transfer_data()` clearing the SPI completion
flag but starting a transaction only for `ESP_IDF_VERSION_MAJOR < 5`. On IDF 5,
it immediately enters a completion loop without starting the transfer.

A test with the **unaltered official v4.1.1 ESP32-S3 Wi-Fi release binary**
also reproduces this hang, with both OLED and I2C sections removed.

A small local patch adding the IDF 5 S3 HAL configuration/start calls fixes
startup on this hardware. All four TMC communication tests then pass.

## Steps to reproduce

1. Build the v4.1.1 ESP32-S3 Wi-Fi firmware with the toolchain above and without
   the proposed TMC SPI patch, **or use the official v4.1.1 `wifi_s3/firmware.bin`**.
2. Use the XYYZ TMC5160 configuration described above; OLED is not enabled.
3. Boot and capture serial output at 115200 baud.
4. Startup stops after the Z positive-limit description, before any TMC
   communication-test result. No G-code or homing command is required.
5. Apply the patch below, rebuild and flash the application only, retaining
   the same configuration.
6. All four driver tests pass and startup completes.

This was reproduced with the complete machine config, not independently
minimized to a single-driver configuration. Please do not interpret the last
printed Z line as evidence that only the Z driver is affected.

## Expected behavior

TMC SPI transfers start and complete. Working drivers pass their tests, and
startup continues. A missing driver should produce a communication error,
not leave the CPU waiting forever for a transfer that was never started.

## Relevant code and proposed fix

`Axes::init()` prints all axis descriptors and then calls `config_motors()`,
which configures motors starting with X. This explains why the last printed
line describes Z even though the first SPI transfer can be where execution
stalls.

In `FluidNC/esp32/tmc_spi_support.c`:

```diff
     spi_ll_clear_int_stat(hw);
 #if ESP_IDF_VERSION_MAJOR < 5
     spi_ll_master_user_start(hw);
+#else
+    spi_ll_apply_config(hw);
+    spi_ll_user_start(hw);
 #endif
     while (!spi_ll_usr_is_done(hw)) {}
```

The installed IDF 5 ESP32-S3 HAL exposes both functions. `spi_ll_apply_config()`
latches the register configuration; `spi_ll_user_start()` starts the user
transaction. Please review the correct equivalent for any other supported
IDF 5 targets before applying this branch generically.

## Validation

- A host regression harness compiles the **actual** `tmc_spi_support.c` against
  a HAL shim, exercising register writes and full-duplex transfers.
- Unpatched: IDF 4 branch passes; IDF 5 branch fails because completion is
  polled before a transfer has started.
- Patched: both branches pass; the IDF 5 test also requires configuration to
  be applied before starting.
- Hardware with the same full config now reports:

### Working release comparison

We subsequently rolled the same controller back to **official v4.0.3
ESP32-S3 Wi-Fi**, preserving the same machine configuration (OLED/I2C omitted),
filesystem, card and wiring. All four TMC driver tests pass, startup completes,
and the user reports SD file loading works correctly. Its application image
reports ESP-IDF 4.4.7. The v4.0.3 application SHA-256 is
`c49c3128ad12319c955b1b253713162215f9b997259fd0445a5b1566fd191ce9`.

This is a useful working baseline, but it predates the upstream ESP-NOW
pendant support introduced in v4.0.4, so it does not meet our wireless-pendant
requirement.

## Separate issue, deliberately not claimed fixed here

After fixing TMC initialization, loading G-code from SD through HTTP/WebDAV
can exhaust memory and panic in the ESP-IDF SD/SPI DMA read path. That has a
separate captured backtrace. This patch fixes the TMC startup hang; it is not
claimed to fix SD download performance, memory pressure or that later crash.
The later no-OLED patched build also reproduced an `async_tcp` watchdog
timeout while serving an SD file through WebDAV. These runtime failures are
not attributed to the missing SPI-start call in this report.
